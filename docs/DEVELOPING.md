# Developing Email

How the app is built, run, tested and how it works inside. For what it does and how to install
it, see the [README](../README.md).

```
crates/mail-core   sync engine, storage, MIME parsing/sanitizing — no UI dependencies
crates/mail-cli    `mailsync`: headless benchmark driver for sync strategies
app/               SolidJS UI (app/src) + Tauri shell (app/src-tauri)
```

## Run

```sh
cd app
npm install
npm run tauri dev        # desktop app
npm run dev              # UI only, in a browser, against an in-memory mock backend
npm run screenshots      # regenerate docs/screenshots/ (needs Google Chrome)
```

Microsoft accounts (outlook.com, hotmail and the like, and Microsoft 365 work or school accounts) sign in on Microsoft's page in the browser: OAuth 2.0 with PKCE and a one-time listener on 127.0.0.1 (`crates/mail-core/src/oauth.rs`); the refresh token goes in the keychain and access tokens are renewed before they expire, for IMAP and SMTP (XOAUTH2). The add-account form switches to "Continue with Microsoft" when the address is Microsoft's (known domains, else MX records). Work accounts need IMAP (and, to send, Authenticated SMTP) enabled for the mailbox. The app's Entra registration (client ID in `oauth.rs`) is multitenant + personal accounts, public client, redirect `http://localhost`. Gmail and Google Workspace sign in with an [app password](https://myaccount.google.com/apppasswords) (requires 2-Step Verification), or on Google's page (scope `https://mail.google.com/`, the only one IMAP and SMTP accept) with the user's own OAuth client if they set one (`docs/GOOGLE.md`), else the app's: release builds have it built in (`oauth::built_in_google_client`, from `MAIL_GOOGLE_CLIENT_ID` / `MAIL_GOOGLE_CLIENT_SECRET` at compile time, which CI sets from the repository secrets `GOOGLE_CLIENT_ID` / `GOOGLE_CLIENT_SECRET`; `google_status`'s `builtIn`). That client is published but not verified by Google: a sign-in shows Google's unverified-app warning, and at most 100 users can sign in with it until it is: `Core::add_google_account`, and `Core::google_sign_in` to sign in again or to switch an app-password account over (Settings › Accounts › Password › Sign in with Google instead…). The account's `auth` is `google`; its refresh token is where a password would be, and the client it was issued to is kept beside it (`<email>#google-client`), so a later change of client in Settings doesn't strand it (one kept with the app's client's ID is used as this build has it, so a new secret reaches it). Tokens are renewed by the same `oauth::Session` as Microsoft's. Google Workspace and Microsoft 365 custom domains are detected from the domain's MX records. Passwords are kept in the system keychain (Secret Service on Linux, Keychain on macOS, Credential Manager on Windows) in one item, `dev.mail-client` / `secrets` (on Windows in pieces of 1,000 characters, `secrets.1` …, under a marker: Credential Manager holds at most 1,280 characters an item); if the server rejects one, the account's sync pauses and the sidebar asks for a new one.

The browser mock takes URL flags: `?empty` (onboarding), `?auth` (rejected password), `?limited` (connection limit), `?error` (sync error), `?many` (six accounts), `?demo` (no test samples, already synced: what the screenshots use); they can be combined.

`npm run screenshots [name]` serves the preview with `?demo`, pins the clock, time zone and window size, and saves each scene in `app/scripts/screenshots.js` to `docs/screenshots/` (unchanged UI, unchanged files). Add a scene there for a new feature, and reference its image in the README.

Data lives in `~/.local/share/dev.mailclient.desktop/` on Linux (`~/Library/Application Support/dev.mailclient.desktop/` on macOS, `%APPDATA%\dev.mailclient.desktop\` on Windows): `mail.db` (accounts, folders, headers, threads, search index) and `bodies.db` (raw messages). Window size is in `~/.config/dev.mailclient.desktop/window.json`.

## Behaviour in detail

- **Conversations:** grouped by Message-ID / In-Reply-To / References (no subject matching), across folders. Only `<…>`-delimited ids count (encoded-word ids are decoded; prose and ids that are really addresses are ignored), so damaged headers can't glue unrelated conversations together. By default a conversation shows only the current folder's messages; the View menu in the message list switches the app-wide default to *All mail* and/or *Include Trash*, and each conversation offers a temporary "Show N more messages in other folders / in Trash".
- **Writing mail:** New message, Reply, Reply all and Forward open a compose window per draft (its size remembered). Rich text (bold, italic, underline, text colour and highlight from a palette each (`TEXT_COLORS`, `HIGHLIGHTS`: colours readable on the white mail is read on; `==text==` and ⇧⌘H highlight in yellow; a highlight's text stays dark in the editor's dark theme too), links, code, headings, lists, quotes, code blocks, lines; the toolbar's tooltips give each key, and Markdown works as typed: `` `code` ``, ```` ``` ````, `#`–`###`, `---`, `**bold**`, `- `, `1. `, `> `). Code, code blocks, headings and lines carry inline styles (`CODE_STYLE`, `HEADING_STYLES`… in Composer.tsx), since the recipient's mail app has none of the app's CSS; the editor shows them in the theme's colours. A code block made from several selected lines is one block, a line each (`CodeBlockLines`), and turns back into a paragraph per line. In the plain-text part a code block keeps its lines and indentation, fenced with ```` ``` ````, inline code is in backticks and a line is `---` (`compose::plain_text`); replies and forwards put your text above the original (Gmail-style quote, the original's attachments carried along on a forward). Recipients are chips: suggestions come from everyone you've corresponded with (not senders seen only in Spam), ranked by how often and how recently you wrote to them, older messages counting less (half-life 180 days); a suggestion can be removed for good (× or Shift+Delete); a chip can be clicked to edit in place. Attachments come from the file picker or drag and drop (Gmail's 25 MB limit is checked before sending). Drafts are saved as you type and listed in Drafts; closing asks whether to keep or discard. A draft opens again with Edit draft, a double-click or Enter on its row. Drafts here are kept by the core and never uploaded; one from the server (written in another app, or on the phone) opens as a new draft here (`openDraftMessage` in `lib/compose.ts`): its recipients (Bcc too, from `MessageDetail.bcc`), subject, text, and its attachments copied into the data folder (`draft_attachment_files`), with `replaces` set to it. The core moves that server copy to Trash the first time the new one is saved with a change, or when it's sent (`retire_replaced_draft`), so Drafts never shows both; closed unchanged, it's left alone. Sending queues the message for 10 s ("Sending… Undo" brings it back into a window), then goes out over SMTP (`lettre`, the server worked out from the IMAP host: Gmail, Microsoft 365, iCloud, Fastmail, Yahoo; same password). The message shows in Sent at once, marked as sending, and the server's copy replaces it; the original is marked replied/forwarded (arrows in the list) (`crates/mail-core/src/compose.rs`, `smtp.rs`).
- **Address book:** the people icon at the top of the sidebar (Ctrl/⌘+Shift+B) shows it over the mail: everyone kept, searchable (names, addresses, companies, phones, notes), and the one chosen, to change (name, company, addresses, phones, notes), write to, see their mail (a search for `from:` them in all folders) or delete; Esc goes back. The Sender panel says "In contacts", or "+ Add to contacts" (prefilled). Its people come first in the composer's suggestions, under their names there, found by name, company or address (`address_book` in mail.db, `crate::addressbook`; the suggestions from mail follow, without repeats). With sender pictures on, each contact has its picture beside it, asked for only once its row scrolls into view (`Avatar`'s `lazy`).
- **Writing help (AI):** Claude with the user's own Anthropic API key (Settings › AI: kept in the keychain as `#ai:anthropic` beside the passwords; model Opus 5.5 by default, Sonnet 5.5 or Haiku 5.5). In the composer, ✨ AI (Ctrl/⌘+J) opens a panel: say what to write and it drafts a reply (with the original, as plain text) or a new message, or rewrites what's written (improve, shorter, more formal, friendlier, fix spelling, translate). The answer streams into the panel; nothing in the message changes until "Use this". `crates/mail-core/src/ai.rs` builds the prompts (the email text in tags, never taken as instructions; plain text out, no signature) and calls the Messages API over the core's own TLS (raw HTTP, SSE parsed as it arrives; effort `low`; server-side refusal fallbacks on Opus/Sonnet); text comes as `ai-text` events and whole in `ai_run`'s answer. Nothing is sent unless asked; `cargo test -p mail-core ai::tests::live -- --ignored` tries the real API with `ANTHROPIC_API_KEY`.
- **Sender panel:** Ctrl/⌘+2 (or View options) shows a pane beside the reader with everything from the sender of the message on screen (for one of our own, whom it's with: the newest someone else in its conversation), in every folder but Trash and Spam, newest first, each in its most specific folder (`Store::sender_of` / `messages_from`; for a conversation, its newest message's sender). A click picks a row and opens the message in its folder; ⌘/Ctrl-click picks one more (or fewer), ⇧-click a range, ⌘/Ctrl+A (with the panel focused) all there are; then Mark read, Move to… (the list's folder picker, for the sender's account, the folders their other mail is in first), Archive, Delete (or the Delete key) or Forward as attachments: one action per folder they're in, one Undo for all. A move leaves those already in the folder where they are; the toast counts only the ones moved, and says how many were there already. It follows the selection a moment after it settles, and looks again when mail changes, keeping what's picked (`components/SenderPane.tsx`). Deleting, archiving or moving there what the overview has open moves it on to the next row that stays (`advancePastRemoved` in `lib/actions.ts`: in conversations, the rows after the open one are checked in order up to the first that stays; if that lookup fails, the delete still happens), and Undo puts the selection back.
- **Several messages:** in the folder list ⌘/Ctrl-click picks a row more (or fewer), ⇧-click a range from the last one clicked, ⇧-arrows extend it, ⌘/Ctrl+A (Edit › Select All outside a text field) takes every row; Esc or moving on picks one again. The picked ids are `state.picked` (messages, or conversations when grouped; rows not loaded come from `list_item_ids`, in the list's order with its filter). While two or more are picked the reader's place shows how many (and, from `selection_info`, their messages and size) with the action bar for all of them: Archive, Delete, Move, Spam, read/unread, star, snooze, tags, and Forward, which forwards them as attachments (each whole message as an `.eml`, `SendRequest.forwardMessages`; `Core::whole_message` downloads those stored without their attachments). Removing them drops the rows at once; Undo brings them back picked. Search results pick one at a time.
- **Signatures:** Settings › Signatures edits them (rich text, saved as typed); which one each address sends with, for new messages and for replies and forwards, is chosen in the account's addresses (Settings › Accounts › the account › Identity) (under each signature, "Used by" lists the addresses that send with it (their own choice or their account's) and for what, each a link to its account's page; deleting one says how many addresses lose it) (`signatures` / `signature_defaults` in mail.db, `crate::signatures`; sanitized to plain formatting when saved, since the composer shows them in its own page). A new message, reply or forward starts with the default of the address it's from (its own, else the account's); the composer shows it under the text with a picker (another one, or none), apart from the editor so switching never touches what's written; changing From switches to that address's default unless one was picked by hand. Sent as the text, a blank line, then `<div class="signature">`, above a reply's quote (`lib/signatures.ts`). The toolbar's HTML button edits a signature as HTML instead (paste one made elsewhere, with colours, fonts and a table layout), with the sanitized result shown under it; one that needs it opens that way, and going back to the simple editor asks first. The signature sanitizer keeps inline styles (not scripted CSS), `<font>` and the table/layout attributes. Pictures (a logo) are pasted, dropped or picked in the editor, scaled to 800 px at most (PNG, or JPEG when big) and sized by dragging a corner; kept as `data:` URLs (the sanitizer allows them only as an `<img>`'s image `src`), and sent as inline parts of a multipart/related that the HTML refers to by `cid:` (`compose::inline_images`, for any `data:` image in a message), since Gmail and Outlook don't show `data:` images.
- **Send as** (other addresses an account sends from: an alias, an address at a domain whose mail comes to the account, a Gmail "Send mail as" address): an account's page in Settings (Accounts › the account › Identity) has a table of its addresses: its own and its others, a row each with the name mail goes out under (the account's own row is the account's name; another address without one uses it), its signatures for new messages and for replies (another address: the same as the account's own address, shown greyed by that signature's name, None, or its own; stored as null, 0 and the id, the 0 as `new_none`/`reply_none` since the columns reference signatures), and a radio in the Default column for the one mail goes out from unless chosen otherwise; the table's last row adds one, typed in place (`components/SendAs.tsx`; `identities` in mail.db, `crate::identities`; `Core::save_identity` checks the address, at most one default per account; removing the account removes them). The composer's From lists every account's addresses as "Name <address>", starting from the account's default (`ComposeState.fromIdentity`, `SendRequest.fromIdentity`; None: the account's own). Only the From header changes (`identities::sender`): the message goes through the account's own server with the account's own address as the envelope sender, so the server must allow the address (a send to an address no longer the account's is refused; a draft from one falls back to the account's own). A reply or forward goes out from the address the mail came to (`identities::for_reply`, from To, Cc and the server's Delivered-To / X-Original-To / Envelope-To): that address; the account's own if it came to that; an address at the same domain (a catch-all: mail to shop@ answered from the one there); else the default. Reply all leaves every one of the account's addresses out. AI apps' drafts start from the same address. A draft from the server opens from the address it was written from, if that's one of them.
- **Keyboard:** Settings › Keyboard starts from Gmail's or Thunderbird's keys ("Restore defaults" picks which). Each preset uses only that client's keys for the commands both have; commands only one of them (or neither) has get the same key in both. Any key can be added or removed, including ⌘/Ctrl combinations (except those the system or app needs). Enter moves the keyboard into the open message so the arrows scroll it; in a conversation, Enter again goes onto the message in view, ↑/↓ move between messages, Enter/Space expand or collapse one, and the expand/collapse-all toggle (`;` Gmail, `*` Thunderbird) works anywhere. Esc steps back out: to scrolling, then to the list. One list (`app/src/lib/shortcuts.ts`) drives the handlers, Settings, button tooltips and the `?` sheet. A search over the list narrows it to the commands with every word typed in their name, their section or their keys as shown ("f5", "shift"); Esc empties it, then closes Settings.
- **Help:** `?` (outside text fields) opens the keyboard-shortcuts sheet (also View menu, and Help → Keyboard Shortcuts on macOS). `?` in an empty search field, or its `?` icon, shows the search syntax with clickable examples.
- **Trust report:** `docs/TRUST.md` (readable) and `docs/trust/` (the draft spec, schema, verifier instructions, `trust.json` with every claim and its evidence, and verification results). When a change adds a connection, a stored file or a setting that sends anything, update `trust.json` and `TRUST.md`.
- **Drop-downs** are `components/Select.tsx`, not the system's `<select>`: a box like our buttons (`field`, `link` or `plain`) and a menu like the View menu, with the keys a `<select>` has (↓/↑, Home/End, type to find, Enter, Esc). Settings leaves Esc to an open one (`.sel-menu`).
- **Settings** (Ctrl/⌘+,): General (default mail app; a Privacy group with how far sender pictures go, each level with what it looks up, senders whose images always load and whether a rule can cover a whole domain, pictures over plain http, what notifications show, and looking for updates when this copy can update itself; the core keeps the choices it enforces in its `settings` table, `lib/privacy.ts` mirrors them), Accounts, Keyboard, and Troubleshooting (version, the log file, the data folder; Developer Tools in builds that include them). Accounts: + Add account in the title bar; the list of accounts and a page for each (see Account settings below); Storage's figures (here and on the server) are counted once a session or on Recount; Export… shows the export's progress, with Stop.
- **Quick search** (`/` with Gmail's keys, Ctrl/⌘+K with Thunderbird's): SQLite FTS5 over sender, recipients and subject (`msg_fts`, kept by triggers) and the text of downloaded messages (`body_fts`, contentless, rowid = message id), prefix-matched as you type. Bodies are in bodies.db, so `body_fts` is filled from Rust: a background thread (`Core::spawn_body_indexer`, `Store::index_bodies`) takes messages with `has_body=1 AND body_indexed=0`, newest first, 100 at a time, and indexes their text (`mime::search_text`: text parts, HTML as text, attachment names, at most 100 KB, into `body_fts`; the attachments' names (those left on the server too) and, if the user turned on "Search the text in attachments" (Settings › General › Privacy, the core's `attachment_search` choice, off by default), the text in them, at most another 100 KB, into `file_fts`, a table of its own (rowid = message id) so search can look in attachments apart: PDFs, found by type, name or content, up to 20 MB each, and plain-text files (.txt, .csv, .md, .ics, .vcf…; `mime::attachment_text`). A PDF comes from the sender and `pdf-extract` can be made to overflow its stack (a form that draws itself), which aborts the process, or to loop: so the app never reads one itself. It starts its own program again with `--pdf-text` (`pdf_helper`: the PDF on stdin, the text framed on stdout, killed after 20 s, 1 GB of memory on Linux), and a helper that crashes or times out gives no text, the message is indexed without it and not tried again. Without the app (`mail-cli`) PDFs aren't read; the core's tests read them in-process, and `pdf_helper`'s tests run the test program itself as the helper. Attachments stored with the body are read from it; those downloaded later (`attachment_cache`) are added by their omitted part's name and type, and `cache_attachment` sets `body_indexed=0` (with the choice on), so a downloaded attachment is searchable within seconds; the batch's check counts the cached attachments too. Turning the choice on or off marks every message with attachments to be indexed again, so their text comes into the index or goes from it (names stay). Messages with attachments indexed before attachments had their own index are indexed again once (`Store::index_attachment_text_once`, setting `attachment_fts_indexed`; no schema change, so older builds still open the database); `store_body` sets `body_indexed=0` (after writing the body), so a new or replaced body is indexed again within seconds, and a trigger removes a deleted message's text. Bodies are read and parsed without a lock, so the batch's write checks each message is still there, still waiting, and has the body that was read (by its length): one that changed or went meanwhile is left for the next batch. The prefix indexes (`prefix='2 3'`) are about half the index's size but keep typing fast: every term is a prefix search. A query term matches either index (`search::terms` gives one FTS expression per index; the SQL ANDs `m.id IN (… UNION …)` per term). On a 40,000-message mailbox the first indexing took 27 s and grew mail.db by about 85 MB (`store::tests::real_db_body_index`). Syntax: `"phrase"`, `from:`, `to:`, `subject:`, `body:`, `attachment:`, `-exclude`. The message open before a search stays open if the search finds it, wherever it is among the results (`search_index_of`, asked when it isn't in the rows loaded so far); else the reader empties. Scope is the whole account or the current folder; "Search in", a drop-down list, limits plain words to one of a fixed list of fields (`SEARCH_FIELD_SETS` in state.ts: everything, all but attachments, subject + sender + recipients, then each alone; kept as `ui.searchIn`; a choice from the chips before it is kept when it's one of the list's, and every field then there means everything).
- **Reader:** sanitized HTML in a sandboxed iframe; remote images blocked until "Load images", which is remembered per message, or "Always load…" from this sender, or from everyone at its domain (kept in `remote_senders`, a domain as `@acme.com`, which takes its subdomains too; Settings › General lists them, to take one off). Rules for a whole domain are off unless turned on (Settings › General › Privacy; the core's `settings` table, `Core::domain_rules`, mirrored by `lib/domainRules.ts`; the migration that added it turned it on for anyone who had one). Rules believe the From address as far as the account's server checks it (`Core::from_believed`): the topmost `Authentication-Results` counts on Gmail and Microsoft accounts, whose servers write their own on every message, and on others when it carries the name of the account's own IMAP or SMTP server (`mime::auth_server`). There, a sender's rule counts only when it shows a DMARC pass for the From domain or a DKIM pass signed by it (`mime::sender_vouched`, `MessageDetail.sender_verified`), and a domain rule likewise (`MessageDetail.senderDomain` is then None; never offered for gmail.com and the like). Elsewhere a sender could have written that header, so rules trust the From address. A name match only ever makes this stricter. Without this, a made-up From address could load images, which tell the sender the mail was opened. Messages lose links to `data:` pages and link `target`s in cleaning (`data:` stays for pictures). Opening a message marks it read. Right-click a person in a header (the sender, To, Cc; reader and conversation cards) or an email link in the body: New message to…, Copy address, Copy name and address (`components/AddressMenu.ts`). `format=flowed` plain text is reflowed (RFC 3676). Quoted replies get a bar per level (HTML `blockquote` and plain-text `>` lines alike). Trailing quoted history collapses behind "Show quoted text" only when it's safe: exactly one quote, nothing written after it, text before it, and no Outlook-style history in the message itself — inline and bottom-posted replies never collapse (`app/src/lib/quotes.ts`; `node app/scripts/quotes-selfcheck.js` checks the plain-text rules). Pictures shrink to fit the reader and keep their shape: one declared at a fixed size (width and height attributes, or inline style, often in inches from Outlook) gets that size's aspect ratio with `height:auto` (`app/src/lib/images.ts`); a shrunk picture can be clicked to see it at its actual size and again to fit, wired from the app side since the frame runs no scripts. A picture from a plain `http://` address is upgraded to https by the webview, as on any secure page; if that fails (a server whose certificate has expired there, say) the frame asks the app for it instead (`rescueHttpImages`, the `mailimg:` scheme, fetched by `icons::mail_image` over plain HTTP: public addresses only, checked on the address connected to and again at each redirect, NAT64 and 6to4 forms included; pictures only, up to 15 MB, four at a time), only for a message allowed to load remote pictures, as its frame's CSP lets `mailimg:` through only then, and not at all when Settings › General › Privacy turns it off (`Core::http_pictures`, checked by the scheme's handler). Cookies that pictures' servers set are removed from the web view at every start and every hour (`forget_cookies`; the app uses none). The data folder is made private to the user (0700) when the store opens, and so is the folder of opened attachments. The address asked for is the browser's (`img.src`, not the attribute's text), and `icons::get` refuses any address with a control character or space, or a host with anything but a name or address, since it writes them into its request as they are. Sender-picture lookups use the same public-only connection. Under the subject band (fixed, with the actions), the reader is one page that scrolls (`.reader-scroll`): sender, recipients, attachments and the message together, each at its natural height, so an expanded recipient or attachment list only makes the page longer and nothing scrolls inside it. Once a message's own header has scrolled out of sight, a one-line strip stands in for it at the top (`components/WhoStrip.tsx`): the sender and recipients, and in a conversation card also the date, a paperclip and the card's actions. It overlays the message (no room taken, no shift) and is sticky inside its card, so the next card's strip pushes it off; a click brings the header back. The reader's leaves out the date and paperclip, which its band shows all the time; the band's "N attachments" scrolls to the attachment chips. Message frames grow to their content in the reader and in conversations alike (`components/AutoHeightFrame.tsx`, the frame's own scrolling off), and a message wider than the pane (a picture at actual size, a too-wide email) widens the reader's page or its conversation card, so the pane scrolls sideways; the message frames never scroll themselves.
- **Attachments:** chips under each message's sender (`components/Attachments.tsx`), one per file with its name and size, up to three rows; past that, "+N more" shows the rest in place ("Show fewer" folds them again) (~ and a cloud while it's still on the server). A click opens it in the default app (or saves one that can't be opened); Enter opens, ⌘/Ctrl+S saves; right-click (or the menu key) for Open, Save to Downloads, Save As… (the system's save dialog, from the core: `save_attachment_as`), and with several, Open All and Save All; "Save all" after the chips too. Room for the row is kept from the list's `hasAttachments` so nothing moves when the names arrive. Files go straight into Downloads (`name (1).ext` if taken), with "Show in folder". Every file written from an email (saved or opened) is marked as downloaded from the internet: the Mark of the Web on Windows, the quarantine flag on macOS (`mark_downloaded`). Attachments left out of the body download are fetched on demand (just that MIME part, on the interactive connection) and cached in `bodies.db`. Only known kinds of documents, pictures, sound, video and zip files open directly (`mime::is_openable`, a list of what opens, not of what doesn't); anything else is only saved. File names are sanitized. While a search is shown, the chips of attachments with one of its words (those looked for in attachments: plain words with Attachments in "Search in", and `attachment:`) get an accent ring: `attachment_matches` reads the message's attachments when it opens (names, and with "Search the text in attachments" on their text, PDFs through the helper), a moment after typing stops (the index only knows which message matched, not which attachment).
- **Message actions:** Archive, Delete, Move to…, Spam/Not spam, Mark read/unread, Star, Tag and Undo, from the keyboard, the reader header (all messages being viewed) or per message in a conversation card. After archiving/deleting, the next older item opens; Undo puts the message back and selects it again. Changes apply locally at once and go to the server through a persistent outbox; moves wait 5 s so Undo just cancels them, and sync waits for pending actions so nothing reappears. Gmail: archive removes `\Inbox` and user labels (unfiled; from Trash/Spam it moves back to All Mail), delete moves to `[Gmail]/Trash` (where the message keeps its labels but shows under none of them), move swaps labels. Other servers: `UID MOVE` to the `\Archive`/`\Trash`/`\Junk` folder (COPY + `\Deleted` without MOVE). A server rejection rolls the change back with a notice (`crates/mail-core/src/actions.rs`). Spam / Not spam also teach the filter: Gmail learns from the move itself; other servers that keep keywords get Thunderbird's `$Junk`/`$NotJunk` first; Microsoft accounts with Graph get a junk / not-junk report (`reportMessage`, which a failure never undoes).
- **Tags (Thunderbird-compatible):** tags are IMAP keywords on the message (`$label1`–`$label5` = Important, Work, Personal, To Do, Later; custom tags use Thunderbird's keyword for the name), so they sync with Thunderbird and other clients. Names and colours are local (seeded with Thunderbird's defaults); keywords without a definition still show. Colored dots and a tinted sender in the list, chips in the reader, a Tag menu, `1`–`9` / `0` shortcuts, Manage tags…, and `tag:work` in search (`crates/mail-core/src/tags.rs`).
- **Sorting and groups:** the View menu sorts the list by Received (newest first), Size (largest first, grouped in eM Client's size ranges, each row showing its size) or From or To (the sender, or the first recipient of To then Cc, as shown: A to Z, newest first within each; `crates/mail-core/src/sort.rs`, whose keys are SQL functions on every connection, so the order, the groups and `index_of` / `next_unread` agree; case-folded across Unicode, nobody last). The list is grouped by the same thing, with a header above each group's first row: by date in periods (Today, Yesterday, this week's days, Last week, Two and Three weeks ago, this year's months, then years; `app/src/lib/listGroups.ts`, in local time, the week starting as the locale says), by sender or recipient one per person with a count. Rows keep their index (a header only makes its row's slot taller), so selection, paging and the keyboard work as without. Conversations only sort by date: From and To show single messages, and "Group by conversation" comes back with Received. Search results stay newest first, ungrouped.

## Export and removal

Settings › Accounts › Export… writes an account's mail to a new folder: one mboxrd file per mail
folder, in subfolders like the account's, and a README.txt with counts and anything that
couldn't be fetched (`crates/mail-core/src/sync/export.rs`). Gmail, like Google Takeout:
each message once, in `All Mail.mbox`, with an `X-Gmail-Labels` header listing its labels (the
other folders it's in); Spam and Trash in files of their own; an account hiding All Mail from
IMAP is exported folder by folder. Messages stored whole are written
from `bodies.db`; those stored without attachments, or not downloaded, are fetched from the
server on a connection of the export's own, only for the export (never stored). One export at a
time, in the background (`Core::export_account`; `export-progress` / `export-finished` events),
shown in the sync status row; closing the main window (or quitting) while it runs asks first
("confirm-close"), and stopping it leaves the folder named "… (incomplete)". Remove account deletes the account's local data (cascading from `accounts`),
its keychain entry, and compacts both databases in the background; nothing changes on the
server.

Secrets (passwords, sign-in tokens, the API key) are one keychain item, `secrets` under
`dev.mail-client`: a JSON object of name → secret (`Secrets` in `crates/mail-core/src/lib.rs`;
on Windows split in parts, as Credential Manager keeps little in one). It's read once and kept in
memory for reading; a change (a secret saved or removed) reads the item again first and changes
only that secret, so another copy of the app's saves are never put back over (`vault_updated`).
When the item can't be read, or is missing while the app knew of secrets (a keychain that didn't
answer properly), nothing is saved. Each save is logged with the secret's name, never its value
or the account's address ("keychain: secret saved").

## Microsoft Graph (tags and snooze on Exchange)

Exchange keeps no custom IMAP keywords, so a Microsoft account the user allows it for
(Settings › Accounts › Tags & snooze; `accounts.graph`) keeps them through Microsoft Graph
(`crates/mail-core/src/graph.rs`): tags as Outlook categories by name (the account's category

an extended property of the app's own. Changes go out through the outbox (`ServerOp::Graph`,
every copy found by Message-ID); changes made elsewhere come in by `sync::graph_task`, every
3 minutes and after our own. IMAP flag sync leaves those keywords alone on such accounts.
Turning it on is a browser sign-in that adds `GRAPH_SCOPES` (Mail.ReadWrite,

## How sync works

- **Folders first.** `LIST` on connect gives the full folder tree in one round trip; a separate connection fills in counts with `STATUS`.
- **Headers in chunks, newest to oldest** (default 5000), addressed by sequence number. The cursor (lowest UID stored) is persisted, so a restart resumes. The focused folder always goes first, and switching folders takes effect after the current chunk.
- **Gmail:** Inbox, `[Gmail]/All Mail`, Trash and Spam are synced directly. Every other label's contents come from `X-GM-LABELS`, and messages are de-duplicated by `X-GM-MSGID`, so each message is stored and downloaded once however many labels it has.
- **Push:** IMAP IDLE on the Inbox and on the folder on screen. A push re-syncs that folder immediately, and bodies of new mail are fetched right away. Every folder is also polled every 60 s.
- **Incremental:** new mail above the highest UID; flag/label changes via CONDSTORE `CHANGEDSINCE`. When counts disagree, expunged and missed messages are found by walking newest-first with `UID SEARCH lo:hi` (sequence ranges → UIDs) until each UID's sequence number equals its rank in our copy; two doubling steps cover the newest 15k messages, deeper changes use one `UID SEARCH ALL`. Every folder also gets a full UID comparison once a day, which catches errors that cancel out in counts.
- **Non-Gmail copies:** a message's identity is its `EMAILID` (RFC 8474 OBJECTID) or else Message-ID + size, so copies in several folders are stored and downloaded once. A message that leaves every folder parks its body in a stash for a week, so a move seen as expunge-then-new doesn't download it again.
- **Bodies (attachments on demand, unless kept):** `BODYSTRUCTURE` decides what to fetch. Messages without attachments come down whole. Others fetch only text parts and inline images under 2 MB, and are rebuilt into a valid MIME message tagged `X-Mail-Partial`. Omitted attachments are recorded (`messages.omitted`) and still listed in the reader. Stored in `bodies.db`, newest first, preferring the folder on screen, over 3 background connections. A message you open is fetched immediately on a dedicated, pre-connected connection. An account set to keep attachments (Settings › Accounts › Offline, off by default) downloads every message whole, and once turned on also re-fetches, after anything still missing a body, the messages it had stored without them; Settings shows how much that is, live. Turning it off stops further downloads; removing what's stored is a separate step (Remove, shown once it's off): each message is rewritten locally into the copy a download without attachments would have made (`partial::strip_local`: same rules, IMAP section numbers kept so attachments are fetched again when opened), then `bodies.db` is compacted (`VACUUM`) to give the space back.
- **Robustness:** timeouts measure inactivity, not total time: a connection that moves no data for 60 s is abandoned and replaced (Gmail stalls connections during bulk downloads). A message that fails is retried alone and fetched whole without `BODYSTRUCTURE` (some malformed structures make the IMAP parser wait forever); after 3 failures it's skipped for the session.
- **Resumable:** the header cursor and every body are committed as they arrive, so quitting mid-sync loses at most one chunk.
- **Connections:** 3 per account when synced (sync, interactive, Inbox IDLE), 4 while a non-Inbox folder is on screen; the 3 download workers connect only while bodies are pending. Folder counts are swept on the sync connection; a push also recounts its own folder.
- **Connection limits:** a sign-in refused as temporary (Gmail's "Too many simultaneous connections", `[LIMIT]`, `[UNAVAILABLE]`, `[INUSE]`, `[OVERQUOTA]`) shows as "Connection limit · retrying" and is retried with jittered backoff; only genuine credential failures pause the account and ask for a password. One app instance runs per machine (a second launch focuses the first).
- **Strategies are pluggable:** implement `mail_core::sync::HeaderSync` and register it in `strategy_by_name` to compare approaches with `mailsync bench`.

## HTML email

Bodies are sanitized in Rust (ammonia; scripts, handlers and forms removed; tables, inline styles and `<style>` kept). `cid:` images are inlined. The reader renders the result in a sandboxed iframe with no script execution and a CSP that blocks remote content until you click "Load images". Links open in the system browser.
